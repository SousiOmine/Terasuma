# Terasuma

ローカルで動く AI エージェントです。チャットと、MCP サーバーが公開するツールの呼び出し、podman のコンテナの中のデスクトップ操作までを実装した状態です。

- 会話は Tera ごとに 1 本、この端末の中だけに保存されます
- 既定では `127.0.0.1` のみに公開します（認証なし）
- 日本語を既定とし、英語に切り替えられます（左下の「設定」から）
- 使用するモデルとプロバイダは画面の「設定 > モデル」から設定します
- MCP サーバー（ローカルのコマンド・HTTP・OAuth）は画面の「設定 > 詳細設定」から繋ぎます。繋いだサーバーのツールをモデルが呼び出します
- エージェントは podman のコンテナの中のデスクトップを操作します（画面の撮影・クリック・キー入力・シェル）。同じ画面をブラウザの右ペインで見られ、ログインのように人の手が要る場面では操作を引き受けられます

## 必要なもの

- [Bun](https://bun.sh) 1.2 以降
- [podman](https://podman.io)（コンテナを操作させるとき。Linux では rootless のまま使えます。macOS と Windows では `podman machine` の VM の中で動きますが、未確認です）

## 使い方

```bash
bun install
bun run dev
```

起動時に表示される URL を開きます（既定は `http://127.0.0.1:3000`）。指定したポートが埋まっていた場合は、空いているポートで起動します。

初回は使用するモデルが未設定なので、チャット画面の案内から「設定 > モデル」を開き、「プロバイダを追加」で API キーを登録してください。手順は「[モデルとプロバイダの設定](#モデルとプロバイダの設定)」に書いています。

ツールを使わせたいときは「設定 > 詳細設定」で MCP サーバーを追加します（「[MCP サーバー](#mcp-サーバー)」）。

コンテナを操作させたいときは、起動時にコンテナも立ち上がります（初回はイメージを作るため数分かかります）。状態と操作は「設定 > コンピュータ」にあります（「[コンテナ](#コンテナ)」）。

### API キー無しで画面だけ試す

モックの LLM で UI とストリーミングを確認できます。`TERASUMA_ENGINE=mock` を明示したときだけ使われ、自動で選ばれることはありません。

```bash
TERASUMA_ENGINE=mock bun run dev
```

## Tera

会話の持ち主を「Tera」と呼びます。Tera は 1 体のエージェントで、会話の履歴を 1 本だけ持ちます。チャットセッションのような「会話ごとの入れ物」は無く、話した内容はその Tera の履歴に積み重なっていきます。

既定で 1 体だけ用意され、画面ではサイドバーに並びます。名前を変える・増やす・役割や人格を持たせる導線はまだありません。

モデルへ渡す文脈は、いまは保存済みの履歴そのものです。Tera ごとに自動で組み立てる形（ユーザーには見せない）に変える予定で、これは別の機会に実装します。

### セッションごとに会話を分けていた頃のデータ

前の版では、会話はセッションという単位で分かれていました。会話の持ち主がセッションから Tera へ変わり、1 体につき履歴 1 本になったため、古い会話はどの Tera の履歴なのか決められません。起動時にテーブルごと作り替え、古い会話は引き継ぎません。

## 保存先

設定と Tera の会話データは、OS ごとの標準的な場所に分けて置きます。

| OS | 設定（config.json） | データ（terasuma.db） |
| --- | --- | --- |
| Windows | `%APPDATA%\Terasuma` | `%LOCALAPPDATA%\Terasuma` |
| macOS | `~/Library/Application Support/Terasuma/` | 同じ場所 |
| Linux | `$XDG_CONFIG_HOME`（既定は `~/.config/terasuma/`） | `$XDG_DATA_HOME`（既定は `~/.local/share/terasuma/`） |

Windows で設定とデータを分けているのは、`%APPDATA%` が別のマシンへ同期される場所だからです。SQLite の DB は、同期の途中でファイルの一部だけが渡ると開けなくなることがあるため、`%LOCALAPPDATA%` に置きます。

`TERASUMA_CONFIG_DIR` と `TERASUMA_DATA_DIR` を設定すれば、それぞれの場所を差し替えられます。

### config.json

設定ファイルは起動時に読み、内容を検証します。無くても起動できますが、その場合は使用するモデルが未設定の状態で立ち上がります。

```json
{
  "model": "deepseek/deepseek-v4-pro",
  "providers": {
    "deepseek": { "apiKey": "sk-..." },
    "custom-1": {
      "baseUrl": "https://gateway.example.test/v1",
      "label": "社内ゲートウェイ",
      "apiKey": "sk-..."
    }
  },
  "modelOptions": {
    "deepseek/deepseek-v4-pro": { "reasoningEffort": "high" }
  },
  "mcpServers": {
    "filesystem": {
      "type": "stdio",
      "command": "bunx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/home/me/docs"],
      "env": { "DOCS_ROOT": "/home/me/docs" }
    },
    "remote": {
      "type": "http",
      "url": "https://mcp.example.test/mcp"
    }
  },
  "port": 3000,
  "engine": "mastra"
}
```

使える項目は `model`、`providers`、`modelOptions`、`mcpServers`、`port`、`engine` の 6 つです。綴り違いに気づかないまま動くと、設定したつもりで効かない状態になります。そのため、未知の項目があると起動時にエラーになります。

- `model` は Mastra のモデルルーター形式の `provider/model`。画面の「既定のモデル」がここに入ります。
- `providers` のキーはプロバイダ名で、モデル ID の先頭部分と一致します。`baseUrl` を持たないものは models.dev のカタログのプロバイダとして扱い、接続先は Mastra のモデルルーターが解決します（`apiKey` が必要です）。`baseUrl` を持つものは OpenAI 互換の独自エンドポイントとして扱い、`label` に画面へ出す名前を持てます。
- `modelOptions` はモデルごとの設定です。いまは思考強度（`reasoningEffort`）だけを持ちます。モデルごとに残るので、別のモデルへ切り替えて戻すと前の値が復元されます。
- `mcpServers` は MCP サーバーの一覧です。キーはサーバー名で、ツール名の先頭に付きます。`type` は `stdio`（この端末でコマンドを起動する）か `http`（URL へ繋ぐ）で、種類ごとに書ける項目が変わります。`stdio` は `command` と、任意で `args`・`env`、`http` は `url` を持ちます。OAuth で認可するかどうかは設定に書かず、繋いだときにサーバーが認可を求めたら始めます。
- 設定ファイルの中身が食い違っていると起動時にエラーになります。独自エンドポイントに `baseUrl` が無い場合、カタログのプロバイダに `apiKey` が無い場合、接続先を持たないプロバイダに `label` を書いた場合、`model` が `provider/model` の形でない場合などです。カタログに無い id は `baseUrl` を要求します。MCP サーバーでは、`type` と食い違う項目（`stdio` なのに `url` があるなど）、使えない id、空の `command` や `url`、環境変数名として読めない `env` のキーを弾きます。

画面から設定を変えると、このファイルが書き換わります。手で編集した内容は、次に画面から変更したときに読み直して取り込みます。API キーは `.env` と同じく平文で保存されるので、置き場所の権限には気をつけてください。

## 設定

環境変数で渡します（Bun が `.env` を自動で読みます）。config.json より優先されます。

| 変数 | 既定値 | 説明 |
| --- | --- | --- |
| `TERASUMA_PORT` | `3000` | 待ち受けポート |
| `TERASUMA_CONFIG_DIR` | OS ごとの設定ディレクトリ | 設定ファイルの置き場 |
| `TERASUMA_DATA_DIR` | OS ごとのデータディレクトリ | 会話データの置き場 |
| `TERASUMA_ENGINE` | `mastra` | `mock` を指定するとモックの LLM になります（開発用） |

`TERASUMA_PORT` と `TERASUMA_ENGINE` は値を確かめます。設定ミスを既定値で隠さないためです。

指定したポートが埋まっているときは、起動を止めずに空いているポートを OS に選ばせて起動します。設定と違うポートで動いていることに気づけるよう、実際に使うポートは起動時のログに「note」として出ます。

モデルとプロバイダは config.json だけに書きます。設定画面と同じ 1 か所にまとめ、環境変数とどちらが効いているのか分からなくなる状態を避けるためです。

## モデルとプロバイダの設定

「設定 > モデル」で、使用するモデルとプロバイダを管理します。プロバイダとモデルの一覧は [models.dev](https://models.dev) のカタログから取ります（約 200 のプロバイダを検索して選べます）。

プロバイダの追加は 3 段です。

1. 接続するプロバイダを選ぶ。models.dev のカタログを検索して選びます。カタログに無い接続先（Ollama や社内のゲートウェイ）は「接続先を自分で決める」から追加します。
2. API キーを入れる（独自エンドポイントと Ollama ではベース URL と名前も入れる）。
3. 「接続を確認」が通ると、カタログから取ったそのプロバイダのモデル一覧が出ます。使用するモデルを選んで追加します。

接続の確認は、プロバイダが公開している `/models` を叩いて行います。公開していないプロバイダ（404 を返すもの）は、その旨を出したうえで確認せずに保存できます。API キーが受け付けられなかった場合（401/403）と、接続先に届かなかった場合は保存しません。

モデルの一覧は models.dev のカタログから取ります。そのためプロバイダ側に `/models` が無くてもモデルを選べます。独自エンドポイントだけはカタログに無いので、`/models` から取ります。

カタログは起動後に一度だけ取得し、データディレクトリの `models-dev.json` に残します（24 時間で取り直します）。models.dev に届かないときは、残っているカタログで動きます。

追加したプロバイダは、カードの「設定を変更」「削除」で管理します。API キーは画面へ戻さないので、変更では空のままにすると保存済みのキーを使います。

既定のモデルは 1 つです。「モデルを変更」で、プロバイダごとのモデル一覧から選び直せます。プロバイダを削除しても既定のモデルは残るので、使えない状態になったときはチャット画面と設定画面が選び直しを案内します。

### 思考強度

既定のモデルが思考強度（reasoning effort）を指定できるモデルなら、「設定 > モデル」の既定のモデルの下に選択欄が出ます。選べる値は models.dev がそのモデルについて公開している値のうち、こちらから実際に渡せるものだけです（例: 低・中・高）。「既定」を選ぶと何も渡さず、プロバイダの既定に任せます。

値はモデルごとに config.json へ保存されます。モデル A を「中」にしてからモデル B へ切り替え、また A を選ぶと「中」に戻ります。

## MCP サーバー

「設定 > 詳細設定」で MCP サーバーを繋ぎます。繋いだサーバーのツールを、モデルがチャットの中で呼び出せるようになります。

サーバーの種類は 2 つです。

1. ローカル（`stdio`）: コマンドを起動して標準入出力で話します。コマンド・引数（1 行に 1 つ）・環境変数を入れます。子プロセスの `stderr` は、Terasuma を起動した端末に出ます。
2. HTTP（`http`）: MCP サーバーの入口の URL へ繋ぎます。認可（OAuth）が要るかどうかは設定に書かず、繋いだときにサーバーが求めたら始めます。

追加は「入力を埋める → 接続を確認 →（認可が要るサーバーなら認可）→ 追加する」の順です。「接続を確認」が通るまで「追加する」は押せません。確かめずに設定だけ残すと、繋がらない理由が分からないまま一覧に並ぶためです。

追加したあとは、サーバーのカードごとに「接続を確認」を押したときだけ実際に繋ぎに行き、公開されているツールが一覧に出ます。設定を変えたときは、保存したあとに一度だけ確かめます。確かめていない間は「未確認」、繋がったら「接続済み」、繋がらなければ理由つきで「接続できません」と出ます。

### OAuth で認可する

HTTP サーバーが 401 を返すと、SDK が認可サーバーの情報を読み、認可の要求を作ります。Terasuma はこれを「認可が必要」として扱い、ブラウザで開く認可画面の URL を出します。

- 追加の途中（「接続を確認」）で認可を求められた場合は、その場で認可へ進みます。ブラウザで認可すると確認が再開され、「追加する」が押せるようになります。待っている間は、開いた画面をもう一度開くための URL をダイアログにも残します。
- 追加ずみのサーバーでは、カードの「認可する」から同じことができます。「認可する」は、繋がらない理由が認可の失効であることもあるため、接続できなかった場合にも出します。
- 認可を待っている間は接続を試しません。繋ぎに行くと認可の要求が作り直され、ブラウザで開いている URL が使えなくなるためです。「認可をやめる」で待つのを止められます。

認可の流れは次のとおりです。

1. サーバーが返した認可サーバーの情報（RFC 9728 / 8414）を読み、クライアントを動的に登録します（RFC 7591。戻り先を `http://127.0.0.1:<Terasuma のポート>/api/mcp/oauth/callback` にした公開クライアントです）。
2. ブラウザで認可すると `/api/mcp/oauth/callback` へ戻ります。PKCE でコードを引き換え、得たトークンをデータディレクトリの `mcp-oauth/` に保存します（本人だけ読める権限で作ります）。
3. 期限が切れたトークンは、保存済みの更新トークンで更新します。待ち受けポートが変わったときは、戻り先が変わるので登録からやり直します。

### ツールの呼び出し

モデルには `<サーバー名>_<ツール名>` の形でツールを渡します（例: `filesystem_read_file`）。呼び出しと結果は本文と同じメッセージの一部として保存され、次のターンの履歴にもそのまま入りますが、チャット画面には出しません。何をしたかを 1 件ずつ追う負担を減らすためです。画面には本文だけを出し、エージェントが動いている間は「作業中…」と出します。

- ツールの一覧は、接続を確かめたとき（起動後はじめてのターンを含む）に取り、それを使い回します。チャットのたびに繋ぎに行かないのは、落ちているサーバーがあると毎回そこで待たされるためです。設定を変えたときと「接続を確認」で取り直します。
- ツール名が他のサーバーのツールと重なった場合は、どちらのツールか決められないので、そのサーバーのツールは渡しません（理由を「接続できません」として出します）。
- ツールを実行する前の確認（承認フロー）はまだありません。サーバーを追加する時点で、そのサーバーのツールがモデルから呼ばれうることを確かめてください。
- 実行の途中で「停止」した場合、結果が残らなかった呼び出しは、次のターンで「中断された」と伝えます（結果を欠いたまま渡すと、プロバイダが呼び出しと結果の対応を取れないためです）。
- サーバーの `env` は画面にも戻します（プロバイダの API キーとは違います）。`config.json` に平文で入っているものと同じ内容で、端末の外には出ません。

## コンテナ

エージェントには、この端末のデスクトップではなく、podman のコンテナの中のデスクトップを触らせます。失敗して壊れるのはコンテナの中だけなので作り直せますし、端末のデスクトップ環境（Wayland か X11 か、どんなアプリが入っているか）に依存しません。画面では、このコンテナを「コンピュータ」と呼んでいます。

コンテナは Debian で、仮想の X サーバ（Xvfb）、ウィンドウマネージャ（openbox）、VNC（x11vnc と noVNC）、Chromium、日本語フォントが入っています。Terasuma 本体はコンテナの外で動き、`podman exec` でコンテナの中のコマンドを呼びます。画面の撮影もクリックもキー入力もシェルも、この 1 本の経路に揃えてあります。

- **状態**: podman に問い合わせた結果をそのまま出します（Terasuma 側に台帳を持ちません）。イメージが無ければ「イメージがまだありません」、コンピュータが無ければ「コンピュータがまだありません」と出ます。状態に色は付けません。
- **起動**: イメージが無ければ作り、コンテナが無ければ作って起動します。順番を覚える必要はありません。
- **停止**: 画面から止める操作は置いていません。止めたいときは端末で `podman stop terasuma` を実行します（次に Terasuma を起動したときは、また立ち上がります）。
- **リセット**: コンテナを作り直します。エージェントが入れたアプリと設定は消え、置いたファイルは「ホームの中身も消す」を選ばない限り残ります。
- **ファイルの置き場**: データディレクトリの下の `container/home` が、コンテナの `/home/agent` に見えます（例: `~/.local/share/terasuma/container/home`）。エージェントが触れるホストの場所は、この 1 フォルダだけです。書き込みの持ち主を揃えるため、コンテナは `--userns=keep-id` で起動します。
- **画面の大きさ**: 1280x800 で固定です。撮った画像とクリックの座標の対応が崩れないようにするためです。

### 右ペイン

チャットの右上のボタンで、コンピュータの画面を開けます（既定は閉じています）。表示は Terasuma の待ち受けポートから中継するので、ブラウザから見えるポートは増えません。閉じている間は接続も張りません。

ふだんは見るだけで、クリックしてもコンピュータには届きません。エージェントから操作を引き受けている間だけ、そのまま操作できます。

### エージェントが使うツール

ツール名は `computer_` で始まります。

| ツール | 内容 |
| --- | --- |
| `computer_screenshot` | いまの画面を画像で返す（大きさも返します） |
| `computer_click` | 座標を指定してクリックする（左・右・中央、回数） |
| `computer_scroll` | 座標を指定してホイールを回す |
| `computer_type` | 文字を打ち込む |
| `computer_key` | `ctrl+c` や `Return` のようなキーを送る |
| `computer_windows` | 見えているウィンドウと、入力先になっているウィンドウを出す |
| `computer_wait` | 指定した秒数だけ待つ |
| `computer_open` | アプリを画面つきで起動する |
| `computer_shell` | コンテナの中でコマンドを実行する（`sudo` も使えます） |
| `computer_ask_user` | ユーザーに画面を渡して待つ（後述） |

画面の撮影は、撮った画像をデータディレクトリの `images/` に置き、会話には参照だけを残します。同じ画面なら同じファイルを使い回すので、撮り直しても増えません。画像は履歴から読み直して、次のモデル呼び出しに渡します（チャット画面には出しません）。

### 操作の引き受け

ログイン、二段階認証、本人確認のように、人の手が要る場面ではエージェントが `computer_ask_user` を呼んでユーザーに渡します。ツールの呼び出しはチャットに出さないので、待っていることは右ペインで分かります。

1. 右ペインが閉じていれば自動で開き、操作できる状態になります。帯に頼まれた内容と「操作を完了した」が出ます。
2. 操作が終わったら、チャットに入力して送るか、「操作を完了した」を押します。
3. 送った文、または「ユーザーは操作を完了しました」がツールの戻り値になり、会話が続きます。

引き受けている間、エージェントは画面を撮らずに待ちます（入力を見せないため）。待っている間も接続が切れないよう、Terasuma は SSE にコメント行を流し続けます。

| `bun run test:live` | 実際の API に繋いで動かす確認（「[実際の API に繋いで確かめる](#実際の-api-に繋いで確かめる)」） |
| `bun run typecheck` | 型チェック |
| `bun run check` | 型チェック + テスト |

### 実際の API に繋いで確かめる

`bun test` は差し替えだけで動きます。ネットワークにも API キーにも触れません。実際のプロバイダへ繋がるかどうかは、`bun run test:live` で確かめます。

```bash
bun run test:live
```

モデルと API キーは config.json から読みます。画面から設定した内容がそのまま確かめられるので、確認用に別の設定を用意する必要はありません。会話はメモリ上に保存するので、端末に残っている会話には触れません。ファイル名を `*.live.ts` にしてあるため `bun test` の探索には載らず、指定したときだけ動きます。

確かめているのは 3 つです。

1. 既定のモデルと 1 ターンやり取りでき、その履歴を積んで 2 ターン目も送れること。
2. モデルがコンテナのシェル（`computer_shell`）を呼び、その結果を答えること。コンテナが無いときは、起動時と同じ手順で起こしてから始めます。
3. モデルがコンテナのデスクトップを操作して画面を撮り、そこに書かれている文字を答えられること（撮った画像がモデルまで届いているかどうかは、ここでしか分かりません）。

API キーが受け付けられなかった場合や接続先に届かなかった場合は、プロバイダが返した理由がそのまま失敗として出ます。通信費がわずかにかかります。

### プロンプトキャッシュを当て続ける方針

DeepSeek 系のキャッシュは、リクエストの先頭が前回と一致するほど当たります。次の規則を守っています。

1. system プロンプトは完全な定数です（`src/server/prompt.ts`）。日時や件数を混ぜません。
2. モデルへは保存済み履歴をそのまま渡します。要約・言い換え・並べ替えをしません。ツールを使ったメッセージは、保存されている呼び出しと結果をその順に assistant と tool の 2 件へ開くだけで、内容は変えません。
3. 履歴は追記専用です。今回は切り詰めを行いません。
4. 可変の情報を渡したくなったら、履歴の末尾（最後の user メッセージの後ろ）に置きます。

`tests/prompt-cache.test.ts` が、規則 2 と 3 を常に満たしているかを確認します。トークン使用量（キャッシュに当たった分を含む）はメッセージと一緒に保存しています。

### 設計上の割り切り

- Mastra の Memory は使っていません。モデルへ渡す文脈を自分で完全に制御し、キャッシュが当たり続けるようにするためです。
- LLM 呼び出しは `AgentEngine` インタフェースを通します。将来ツールや承認フローを足すときも、このインタフェースの内側だけで完結します。
- 1 ターンでモデルを呼ぶ回数の上限は、コードで決めます（いまは 5）。依存側の既定に任せると、こちらの意図と関係なく変わってしまうためです。上限で打ち切られたときは、その理由を本文の末尾に残します。黙って切れると、応答が途中で終わった理由が画面から分からなくなります。
- モデルとプロバイダは config.json にだけ置きます。環境変数と画面の二重管理にすると、どちらが効いているのか分からなくなるためです。
- モデルの指定が揃っていない状態は、モデルを呼ぶ前に理由付きで止めます。既定値で埋め合わせると、設定したつもりで応答が来ない状態になります。
- ポートが埋まっていても起動は止めません。空いているポートで起動し、実際に使うポートを必ずログに出します。設定と違うポートで動いていることに気づけないままにしないためです。
- エラーは機械可読なコードで返し、画面に出す文言はクライアントの i18n で解決します。サーバを言語非依存に保つためです。
- エラーコードの一覧と型は `shared/types.ts` に置きます。一覧を値として持ち、型はそこから導きます。別々に書くと、コードを足したときに片方だけ古くなり、画面が理由を出せなくなります。
- 例外を 1 行の文字列にする処理は `shared/errors.ts` に 1 つだけ置きます。サーバとクライアントで同じ実装を使うためです。
- プロバイダとモデルの一覧は models.dev から取ります。プロバイダごとに一覧の API を実装し分けずに済み、思考強度のようにモデルごとの違いも同じ場所から取れるためです。カタログはデータディレクトリに残し、届かないときはそれを使います。
- 思考強度はプロバイダごとに渡し方が違うので、変換表を `reasoning.ts` に 1 つだけ置きます。表に無いプロバイダは OpenAI 互換の形（`reasoningEffort`）に倒し、渡せない値が設定に入っていたら黙って落とさず止めます。
- config.json の検証はカタログを読まずに行います（Mastra が同梱しているプロバイダの一覧だけを見ます）。models.dev に届かない状態でも起動できるようにするためです。
- MCP の接続は `MCPClient`（`@mastra/mcp`）に任せ、こちらが決めるのは「いつ接続を作り直すか」と「モデルへ渡すツール名」だけにしています。接続先ごとの実装（子プロセスの起動・HTTP・OAuth・ツールのスキーマ変換）を持たずに済むためです。
- MCP サーバーは、追加する前に繋がることを確かめます。確かめていない設定を一覧に並べると、繋がらない理由が分からないまま残るためです。認可が要るかどうかは設定に書かず、繋いだときにサーバーが認可を求めたら始めます（設定に書くと、サーバーの応答と食い違いうるためです）。
- ツールの一覧は接続を確かめたときにだけ取り直し、チャットはその写しを使います。毎ターン繋ぎに行くと、落ちているサーバーの分だけ待たされるためです。「設定を変えたら確かめ直す」という 1 つの規則で揃えてあります。
- ツール名は `<サーバー名>_<ツール名>` にし、重なったら黙って片方を選ばず、そのサーバーを失敗として出します。どちらのツールが呼ばれたのか分からない状態を作らないためです。
- OAuth は公式 SDK（`@modelcontextprotocol/client`）の `auth()` に任せ、こちらは値をファイルへ保存する口（`OAuthClientProvider`）だけを実装しています。認可サーバーの探索・動的クライアント登録・PKCE・更新はライブラリの実装に乗ります。戻り先は Terasuma 自身の `/api/mcp/oauth/callback` なので、認可用に別のポートを開けません。`@modelcontextprotocol/client` の版は `@mastra/mcp` が固定している版に合わせています（同じ実装を 2 つ入れないためです）。
- MCP サーバーの `env` は画面にも戻します。`config.json` に平文で入っている内容そのもので、端末の外へは出ないためです（プロバイダの API キーは、変更で入力し直さずに済むよう画面へ戻しません）。
- 画面の言語だけはブラウザの `localStorage` に保存します。ブラウザが管理する領域なので、アプリ側からは置き場所を指定できません。
- podman は libpod の REST API ではなく、コマンドとして呼びます。rootless の socket を有効にしたり、そのパスや権限をユーザーに用意させたりせずに済むためです。
- 設定にコンテナの項目は足しません。コンテナ名・イメージ名・マウント先・解像度はコードで決めます。効かないつまみを増やすと、どれが効いているのか分からなくなるためです。
- コンテナの状態は podman への問い合わせだけで決めます。Terasuma 側に台帳を持つと、手でコンテナを止めたときに食い違い、どちらが本当か分からなくなります。ただし、同じ問い合わせは 1 秒だけ使い回します。画面の中継は 1 回の表示で何度も聞くためで、起動とリセットの前後は使い回さずに聞き直します。
- podman が無い端末では、コンテナのツールをモデルへ渡しません。呼ばせてから失敗させると、ターンを 1 つ無駄に使ったうえで、モデルは「起動してください」としか言えないためです。
- 撮った画像は、ツールの結果ではなく、その直後の user メッセージとしてモデルへ渡します。OpenAI 互換のプロバイダは tool の本文に画像を置けず、渡しても文字列に潰されるためです（実測）。保存した履歴には参照だけを残し、渡すときに読み直します。
- 画像はデータディレクトリにファイルとして置き、DB には参照（ハッシュ・種類・大きさ）だけを入れます。base64 を保存すると、会話を読み直すたびに大きな文字列を運ぶことになるためです。
- ツールの呼び出しと結果、撮った画面の画像は、チャット画面には出しません。1 ターンの中の出来事を 1 件ずつ追う負担を減らすためです。保存と、次のターンの履歴へ渡すことは今までどおり行います。動いていることは「作業中…」と、右ペインの画面で分かります。
- 引き受けている間のチャットは、新しい発言ではなく `computer_ask_user` の戻り値にします。新しい発言として扱うとターンが 2 つ重なり、会話の並びと保存の順序が崩れるためです。
- 待ちの接続には心拍（SSE のコメント行）を流し続けます。Bun の待ち受けは何も流さない接続を既定の 10 秒で切るためです（実測で 12 秒）。
- 会話はセッションではなく Tera に属します。1 体につき履歴は 1 本で、増やす導線・名前を変える導線・役割や人格は別の機会に足します。
- Tera の行が無いと何も始まらないので、既定の Tera は起動時に 1 回だけ用意します（`ensureTera`。あれば名前も作成日時も触りません）。
- 古い形の DB は、会話を引き継がずに作り替えます。会話の持ち主（セッション → Tera）が変わり、古い会話がどの Tera の履歴なのか決められないためです。
